# Coloroteca

输入任意色值，匹配色库中最接近的色号。输入 `#FF6B6B`，得到最近的 5 个色号、每个的 ΔE2000 色差、以及「肉眼几乎无法分辨 / 一般观察者可辨」这样的人话分级。

网页版和 Agent Skill 共用同一份匹配引擎，所以同输入必得同输出。

---

## 先说清楚这个项目不做什么

**Coloroteca 不内置、不分发任何受保护的色库数据。** 潘通（Pantone）、Freetone 之类的色号列表与色值属于各自权利人的知识产权，不是我们能打包分发的。你自己导入的色库才是本工具的数据源。

所以这个项目真正的资产是两样东西：

1. **色差匹配引擎**——CIEDE2000，用 Sharma 等人的官方 34 组数据逐组验证过（容差 1e-4）。
2. **色库格式适配层**——把 `.ase` / `.acb` / `.gpl` / 文本列表统统读成一套统一的 CLF 格式。

打个比方：这像一个能读 `.ase` 的播放器。播放器不承担音源版权，但能把你合法拥有的音源播出来。

内置的只有两份可自由分发的示例色库（自造色轮 CC0 + MIT 许可的中国传统色 158 色），用来让你先跑起来看看效果。

## 一分钟上手

### 网页版

**方式 A：双击打开（推荐给「只是想用一下」）**

```bash
npm run build            # 生成 dist/coloroteca.html
```

然后双击 `dist/coloroteca.html`。单文件，所有代码和数据都在里面，离线可用，不需要装任何东西。

> 为什么需要打一次包：浏览器不允许 `file://` 页面加载 ES 模块（同源策略，origin 为 null）。源码保持「模块 + 无构建」是给开发和审阅用的，单文件版是给使用用的。打包器是我们自己写的，只做一件事，且会在遇到不认识的语法时直接报错而不是产出坏文件。

**方式 B：跑本地服务（推荐给「要改代码」）**

```bash
npm run serve
# 打开 http://127.0.0.1:8787/
```

源码即产物，没有构建步骤。改完 `web/app.js` 刷新即可。

网页版能干什么：

- 五种输入方式实时联动：HEX / RGB / HSL / 系统调色盘 / **屏幕吸管**（Chromium 系）
- 结果卡片以「输入色为底、候选色内嵌」并排显示，差异直接看得见
- 每个结果带完整色号、色名、HEX、RGB、CMYK、Lab、ΔE2000、感知分级，以及 **ΔL / ΔC / ΔH** 差异拆解
- 色差公式（CIEDE2000 / CIE94 / CIE76）、kL 权重、结果数量、阈值都可在设置里改
- 色库导入（拖拽 / 多选文件 / 整个文件夹 / 粘贴文本）与切换
- 批量匹配：粘一批色值，一次出结果，可导出 CSV
- 色号反查：输入 `185 C` 或 `胭脂` 看它是什么颜色

## 先把色库准备好

没有色库时，`list.mjs` 会明确告诉你这一点并给出获取途径，`--include-demo` 可以先看内置示例。

```bash
node skill/scripts/list.mjs --include-demo                 # 看有什么
node skill/scripts/convert.mjs "PANTONE+Solid Coated.acb" \
    -o ~/.coloroteca/libraries/pms-c.clf.json \
    --system PMS --prefix PANTONE --suffix C --license proprietary
```

支持的输入格式：

| 格式 | 扩展名 | 说明 |
|---|---|---|
| CLF | `.clf.json` | 本项目的原生格式 |
| **ACB** | `.acb` | **Adobe 色库，自带真实油墨 Lab 值——首选** |
| ASE | `.ase` | Adobe Swatch Exchange，Freetone 等用的就是这个 |
| GPL | `.gpl` | GIMP / Inkscape / Aseprite |
| 文本 | `.txt` `.csv` `.tsv` `.css` | 一行一个色值，或 `色号 #色值` |

**为什么 `.acb` 是首选**：Pantone 官方发布的是**油墨 Lab 值**，hex 反而是第三方从 Lab 反推的近似。ACB 文件里存的就是那份 Lab，导入时会被完整保留并直接用于匹配，精度高于任何 hex 往返。ASE 的 LAB 色块同理。

拿到色库的合法途径（官方订阅、开源替代、自己已有授权等）见 **[docs/GETTING-LIBRARIES.md](docs/GETTING-LIBRARIES.md)**。

## 色差怎么读

默认 CIEDE2000。分级阈值是这套公式自己的：

| ΔE | 含义 |
|---|---|
| < 1.0 | 肉眼几乎无法分辨 |
| 1.0 – 2.0 | 受过训练的眼睛可辨 |
| 2.0 – 3.5 | 一般观察者可辨 |
| 3.5 – 5.0 | 明显不同色 |
| > 5.0 | 基本算两种颜色 |

**CIEDE2000 的恰可察觉差异约 1.0，CIE76 约 2.3——两套阈值不可混用。** 本项目的分级只适用于 CIEDE2000。

**kL 明度权重**：图形的印刷/屏幕场景 kL=1；纺织品的表面纹理削弱了人眼对明度的敏感度，故 kL=2。脚本和网页都会按色库的 `meta.system` 自动判断（`TCX` / `TPG` / `TEXTILE` → 2），也可以手动覆盖。

结果里的 **ΔL / ΔC / ΔH** 告诉你差在哪：是偏亮偏暗、偏艳偏灰，还是色相不同。只给一个数字的工具和能解释差异的工具，是玩具和专业工具的分界。

## 匹配精度由你的数据质量决定

这一点必须说白：

- **色库本身的质量是上限。** 第三方从 Lab 反推的 hex 表，反推过程本身就有误差；再怎么算也无法还原。
- **屏幕 ≠ 实物。** 屏幕发光的色域和纸张油墨的色域不是一回事，任何屏幕匹配都只是近似。**实际指定色号请以官方色卡为准。**
- **体系要对得上。** 拿屏幕 RGB 去匹配纺织 TCX 色库、或者忘了切 kL，结果会系统性偏移。

## 项目结构

```
Coloroteca/
├── core/                  ★ 单一事实来源，网页与 CLI 共同 import
│   ├── color-space.js     颜色空间转换（sRGB 分段传递函数、Bradford 色适应）
│   ├── delta-e.js         ΔE76 / ΔE94 / CIEDE2000
│   ├── matcher.js         匹配主流程
│   └── clf.js             CLF 校验与归一化
├── parsers/               格式嗅探与解析 → 统统输出 CLF
├── web/                   纯静态单页（零依赖、无构建）
├── skill/                 Agent Skill：SKILL.md + match/list/convert
├── data/
│   ├── zh-colornames.json 中文色名 → 参考色值（202 条）
│   ├── demo/              内置示例色库（CC0 / MIT）
│   └── libraries/         你的色库（.gitignore 排除）
├── tools/                 serve / build-standalone / install-skill /
│                          make-demo-libraries / make-zh-colornames / scan-protected
├── tests/                 101 项测试
└── docs/
```

**关键设计**：`core/` 是唯一实现算法的地方，网页端和 Skill 端 import 的是同一份代码。这是「网页和 agent 结果对不上」这个问题的唯一可靠解法——不是靠对两边行为，而是让两边根本就是同一个东西。测试里有一条专门交叉验证页面渲染结果与 `core/` 逐位一致。

## 开发

```bash
npm test          # node --test，101 项
npm run check     # 合规扫描：仓库里有没有不该有的色库数据
npm run serve     # 本地服务
npm run build     # 生成 dist/coloroteca.html 单文件版
```

零运行时依赖，零构建步骤。唯一的「构建」是可选的单文件打包（给 `file://` 双击用，因为浏览器不允许 `file://` 页面加载 ES 模块）。

技术决策记录：

- **不用 colorjs.io / culori**：核心算法约 250 行，用 Sharma 官方数据验证过正确性后，自实现 + 权威验证优于引依赖 + 信信任。也让离线分发和长期维护成本归零。
- **不用 γ=2.2 近似 sRGB 传递函数**：暗部误差肉眼可见，必须用标准分段函数。
- **不引入 KD-tree**：2300 条线性扫描亚毫秒级。超过约 5 万条再说。

## 合规

这是本项目的立身之本，所以有工程手段兜着：

- `.gitignore` 排除 `data/libraries/` 与所有 `.ase` / `.acb` / `.aco` / `.act`
- `tools/scan-protected.mjs` 在提交前扫一遍，检测：色库二进制文件、非自由许可的 CLF、粘贴的批量色卡表特征、色名表来源越界、用户色库被误纳入版本管理
- **该扫描器自身不含任何受保护色值清单**——放一份清单进仓库，本身就是把要拒绝的数据放进来；而且只能抓到它已经知道的色库。所以它检测的是**结构特征**，不是内容匹配
- 每个色库必须标注 `source` 与 `license`，这两个字段在 CLF 里是必填的
- 内置数据只有两份，许可分别是 CC0 与 MIT
- 中文色名表刻意剔除带商标/品牌归属的色名（蒂芙尼蓝、克莱因蓝等），并有测试守着不让它们回来
